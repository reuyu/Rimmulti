Proposed ADR-003: Canonical Settlement State, Entity Identity, and Save ProvenanceStatus: PROPOSED (Not Accepted)Decision Owner: Master (GPT-5.6 Sol)Project: WarEconomy / RimMulti1. Context & BaselineThis ADR defines the canonical representation of a RimWorld settlement, the management of persistent entity identity across isolated engine instances, and the validation of state provenance. It adheres to the Master-accepted B2-lite baseline: the canonical state relies on an immutable engine-produced whole target Settlement/Map artifact, a small server-maintained index, and an ordered typed cross-boundary operation journal, deliberately rejecting arbitrary field-level RimWorld object merges.   2. Canonical Settlement Material-State RepresentationThe Canonical Settlement State is composed of three synchronized elements:Artifact (.rws Snapshot): An immutable, hash-verified RimWorld save XML representing the complete target map and its occupants at a specific ArtifactRevision.Server Projection / Index: A server-memory representation of essential settlement data (e.g., total wealth, active pawn count, aggregated trade inventory) required for Tier calculations (FR-015), Territory logic, and Economy without requiring constant engine materialization.   Delta / Cross-Boundary Manifest: An ordered journal of typed operations (e.g., ingress/egress, trade, tax, ownership changes) that have occurred since the last ArtifactRevision and must be applied at the next engine materialization.   3. Revision Hierarchy and Stale Checkpoint RulesTo prevent stale-save duplication and rollback exploits (RISK-03), state is fenced using a strict revision hierarchy:   SettlementStateRevision: The unified canonical head revision. It increments on every accepted artifact checkpoint OR every applied cross-boundary delta.ArtifactRevision: The specific revision of the physical .rws snapshot.InventoryRevision: The revision of the server projection/index, updated synchronously with deltas or new artifacts.Provenance & Stale Checkpoint Rule: Every client or Worker checkpoint upload MUST declare its parent SettlementStateRevision. The server accepts the upload in a fast-forward-only manner; if the parent does not match the server's canonical head, the checkpoint is strictly rejected as stale.   4. Cross-Process Entity IdentityBecause multiple RimWorld engines (various clients, Tactical Workers) generate native loadID values independently, native IDs cannot serve as global identifiers.   EntityId Namespace & Allocation: The Dedicated Server issues pre-allocated EntityId namespaces or lease-ranges to any active Writer Lease (Client or Worker).Native loadID Binding: A custom ThingComp or global mapping component binds the server-issued EntityId to the engine-native loadID.Scope: Stable EntityId tracking is mandatory for Factions, Pawns, Animals, and high-value/transferable Things.Create/Destroy: Newly spawned entities claim a server-issued ID from the writer's leased range. Destroyed entities are logged in the cross-boundary manifest to prevent resurrection.   Split/Merge: When a stack splits, the new stack draws a new EntityId from the leased range. When stacks merge, the absorbed EntityId is explicitly destroyed and logged.   Nested Holders: An EntityId must persist recursively. If a Pawn is transferred, its inventory (and the EntityId of items within) must be preserved in the exported graph.   Canonical Faction Registry: Player Factions (created, dissolved, or split per FR-008, FR-028, FR-176) are globally identified by the server and explicitly projected into every materializing engine instance to prevent ID collisions.   5. Economy and Tactical Ingress/EgressUnder the Master-accepted B2-lite model, concurrent mutations during a Tactical material-state lease are handled via queueing to avoid field-level merges.   Active Tactical Lease: While Settlement S is actively leased by a Tactical Worker, any Auto Shop trade (FR-206) or Tax operation (FR-187) targeting S is strictly queued.   Post-Tactical Resolution: Once the Worker publishes its outcome and releases the lease, the server revalidates queued operations against the new InventoryRevision. Valid operations are applied sequentially; invalid operations (e.g., target items were destroyed) fail or trigger compensation rules (to be defined in ADR-004). Note: TBD-05 (partial tax collection timestamp) remains explicitly unresolved.   Ingress/Egress Manifest: Tactical arrivals (attackers, visitors) and departures (retreating caravans, loot) are represented as typed EntityId transfers in the cross-boundary manifest, evaluated during materialization or publication.   6. Hostile Input Validation BoundaryAn owner client's uploaded save artifact is untrusted hostile input. The "Trusted Worker" is an operator-controlled process, not a consumer of trusted input.   Validation Gate: Before an artifact becomes canonical, the server MUST enforce XML schema validation, size limits, and a strict content/mod allowlist.

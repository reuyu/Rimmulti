
# WarEconomy 요구사항 정규화 및 품질 분석 v1

## 1. 문서 목적

본 문서는 지금까지의 요구 인터뷰, 도메인 분석, 시나리오 분석 및 유스케이스 명세에서 도출된 요구를 정규화한다.

요구사항은 다음 다섯 종류로 구분한다.

- **FR**: Functional Requirement — 기능 요구사항
- **BR**: Business Rule — 게임 규칙 및 정책
- **NFR**: Non-Functional Requirement — 비기능 요구사항
- **CON**: Constraint — 기술·운영 제약
- **CFG**: Configuration Requirement — 서버 설정 가능 요구사항

우선순위는 다음과 같이 사용한다.

- **Must**: 핵심 게임 구조를 위해 반드시 필요
- **Should**: 중요하지만 제한적으로 단순화 가능
- **Could**: 구현 복잡도에 따라 후순위 가능

품질 상태는 다음과 같이 구분한다.

- **PASS**: 현재 상태로 구현 및 테스트 가능한 수준
- **TBD**: 일부 정책값 또는 세부 규칙이 미확정
- **RISK**: 요구는 명확하지만 기술적 실현 가능성 검토가 필요

# 25. 요구사항 품질 분석

## 25.1 명확성

### 결과: 양호

대부분의 요구는 Actor, 행동, 조건, 결과가 명확해졌다.

예:

> "오프라인 Settlement도 공격할 수 있다."

보다 현재 요구는:

> "정당한 공격 권한을 가진 공격자는 Settlement Owner가 Offline이어도 해당 Settlement를 침공할 수 있으며, 방어 Pawn은 AI 제어를 받고 결과는 영구 반영되어야 한다."

수준으로 구체화되었다.

### 잔여 모호성

- 절도 Betrayal 판정
- 완전 Faction 소멸 조건
- 국경 강제퇴거 목적 Tile
- 부분 Tax 납부 Cycle

# 25.3 일관성

### 결과: 양호

초기에 존재하던 주요 충돌은 인터뷰를 통해 해소됐다.

해소된 사례:

- Tribe와 최초 King의 순환 의존
- Alliance와 Betrayal 관계 충돌
- Settlement 0개와 Faction 소멸 혼동
- Tier와 Title의 개념 혼재
- Faction Vision과 Player Vision 혼재
- Visit Session과 Combat Session 중복


# 25.4 검증 가능성

### 결과: 양호

대부분의 FR은 자동 Test 또는 명확한 수동 Test Case로 검증 가능하다.

예:

**FR-085**
WarPending 동안 공격자와 방어자 모두 공격 불가.

→ Test:
1. A가 B에 선전포고.
2. Pending 상태 진입.
3. A → B Attack 시도.
4. 거부 확인.
5. B → A Attack 시도.
6. 거부 확인.
7. Timer 만료.
8. 양측 Attack 가능 확인.

즉 요구와 QA Test Case를 1:1로 연결할 수 있는 수준이다.


# 25.5 추적 가능성

### 결과: 양호

현재 구조는 다음 추적 체계를 만들 수 있다.

`User Requirement → Scenario → Use Case → FR/BR → Design → Test Case`

예:

`오프라인 공격 요구`
→ SCN-19
→ UC-13
→ FR-113/114/115/116
→ Offline Combat Architecture
→ QA Offline Invasion Suite

최종 SRS에서는 이 Traceability를 유지한다.


# 25.6 구현 가능성

전체 요구 중 특히 기술 검증이 필요한 것은 다음이다.

### RISK-01 — Offline Combat

**위험도: 매우 높음**

Map Owner가 Offline인데도 Settlement를 실제 RimWorld Simulation으로 전투시켜야 한다.

현재 선호 Host-Authoritative 구조와 직접 충돌한다.

아키텍처 설계의 최우선 PoC 대상이다.

### RISK-02 — Remote Tactical Session

**위험도: 높음**

Map Owner Client가 전체 Simulation을 수행하면서 Remote Player가 자기 Pawn을 자연스럽게 조작해야 한다.

다음 문제 검증 필요:

- 명령 Latency
- Snapshot 크기
- Projectile
- Pawn Job
- Targeting
- Map State
- Reconnection

### RISK-03 — Persistent Offline Trade Inventory

**위험도: 중간**

Local Simulation이 정지한 Settlement의 실제 Inventory를 서버 거래와 안전하게 연결해야 한다.

중복 Item 또는 Inventory Rollback 방지 필요.

### RISK-04 — Atomic Full-Map Ownership Transfer

**위험도: 중간~높음**

Pawn, Animal, Building, Item 및 각종 RimWorld Reference의 Faction 변경 시 부작용을 검증해야 한다.

### RISK-05 — Intent-Aware Betrayal

**위험도: 중간**

실제 Damage가 아닌 의도한 Attack Target을 추적해야 한다.

특히 AoE에서 기술 난도가 상승한다.


# 26. 현재 품질 게이트

총평:

**요구사항 구조 품질: Gate Pass 가능**

단, 다음 4개 정책은 최종 SRS에서 `TBD`로 남기거나 지금 확정해야 한다.

1. 가입 Player가 새 작위 SettlementLimit을 초과한 경우
2. 절도의 Betrayal 발생 시점
3. WarPending 강제퇴거 Tile 선정
4. 부분 Tax Collection 후 다음 Cycle 계산 기준

Faction 완전 소멸 조건 역시 최종적으로 정의하는 것이 바람직하다.

Offline Tactical Authority는 요구정책 문제가 아니므로 최종 SRS에 **Architecture Risk**로 명시하고 설계 단계에서 해결한다.


# 27. 현재 Requirement Baseline

현재 Baseline은 다음과 같다.

- **기능 요구사항:** FR-001 ~ FR-176
- **비즈니스 규칙:** BR-001 ~ BR-025
- **비기능 요구사항:** NFR-001 ~ NFR-012
- **기술/운영 제약:** CON-001 ~ CON-010
- **서버 설정 요구:** CFG-001 ~ CFG-026

이 Baseline을 기준으로 이후 요구가 추가될 경우 기존 ID를 임의로 재사용하지 않고 Change Request 형태로 관리하는 것이 적절하다.

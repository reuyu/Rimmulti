좋다. 이 답변까지 반영하면 **요구 추출 인터뷰 1차는 종료**해도 된다. 마지막 12개 답변으로 앞서 발견했던 주요 모순도 대부분 해소됐다.

이제 두 번째 단계인 **도메인 분석**으로 넘어간다.

# WarEconomy 도메인 분석 v1

## 1. 시스템 경계

WarEconomy는 크게 세 개의 실행 영역으로 나뉜다.

| 영역 | 책임 |
|---|---|
| **Dedicated Server** | 영속 월드 시간, 플레이어 식별, 세력/작위/외교/전쟁/국경/시장/세금 상태, 서버 설정, 감사 로그 |
| **RimWorld Client** | 정착지 로컬 시뮬레이션, UI, 캐러밴 조작, 전술 세션 렌더링 및 조작 |
| **Tactical Session** | 여러 플레이어가 동일 타일에서 상호작용할 때 생성되는 공동 맵 시뮬레이션 |

중요한 점은 **서버 월드와 정착지 맵이 동일한 시간축을 공유하지 않는다는 것**이다.

`World Time`은 서버가 항상 진행하지만 `Settlement Time`은 각 정착지 로컬 RimWorld 시뮬레이션을 따른다.

따라서 서버에서 겨울이어도 어떤 정착지 내부에서는 여름일 수 있다.

---

# 2. 핵심 Actor

| Actor | 설명 |
|---|---|
| **Player** | 실제 사용자. Steam ID를 우선적인 영구 식별자로 사용 |
| **Faction Ruler** | 해당 세력에서 가장 높은 작위를 가진 플레이어 |
| **King** | 작위 임명·승진·강등·박탈 권한을 가진 통치자 |
| **Emperor** | 제국 최상위 통치자. 왕을 포함한 하위 작위 관리 가능 |
| **Vassal** | 다른 귀족의 봉건 계통에 속한 플레이어 |
| **Caravan Owner** | 캐러밴을 운용하는 플레이어 |
| **Settlement Owner** | 특정 정착지를 소유한 플레이어 |
| **Server Administrator** | 서버 콘솔에서 운영 작업 수행 |
| **NPC Faction / Settlement** | 동적 시장 시스템의 비플레이어 거래 주체 |
| **Defending AI** | 오프라인 플레이어가 공격받을 경우 폰을 대신 제어 |

하나의 Player가 상황에 따라 여러 Actor 역할을 동시에 가진다.

예를 들어 공작 A는 동시에 `Player + Vassal + Settlement Owner + Caravan Owner`이다.

---

# 3. Player 도메인

`Player`는 게임의 최상위 소유권 단위다.

### Player

| 속성 | 의미 |
|---|---|
| PlayerId | 내부 영구 ID |
| SteamId | Steam 기반 식별자 |
| DisplayName | 현재 플레이어 이름 |
| FactionId | 현재 소속 세력 |
| Title | 현재 보유 작위 |
| SettlementIds | 소유 정착지 |
| CaravanIds | 소유 캐러밴 |
| OnlineState | Online / Offline |
| SettlementLimit | 현재 최대 정착지 수 |

중요한 불변조건은 다음과 같다.

**한 Player는 동시에 하나의 세력에만 속한다.**

그리고

**한 Player는 동시에 하나의 봉건 작위만 보유한다.**

작위 승진이나 강등은 기존 작위를 새로운 작위로 **대체**한다.

---

# 4. Faction 도메인

Faction은 플레이어 집단이면서 외교·전쟁의 기본 단위다.

### Faction

| 속성 | 의미 |
|---|---|
| FactionId | 세력 식별자 |
| Name | 세력명 |
| Tier | 현재 세력 규모 |
| Color | 월드맵 표시색 |
| RulerPlayerId | 최고 통치자 |
| Members | 소속 플레이어 |
| Settlements | 세력 소속 정착지 |
| Caravans | 세력 소속 캐러밴 |
| TierScore | 승격/강등 계산값 |
| BetrayerStatus | 배신자 상태 |
| DiplomacyState | 타 세력과 외교 관계 |

Faction Tier는

`Tribe → Minor Faction → City-State → Nation → Empire`

순서다.

기존 단순 Score뿐 아니라 최종적으로는 다음 요소를 함께 평가하게 된다.

| 평가 영역 | 예 |
|---|---|
| 정착지 | 유효 정착지 수 |
| 경제 | 세력 총 Wealth |
| 인구 | 활동 폰 수 |
| 영토 | 연결된 국경 타일 수 |
| 봉건 | 요구되는 통치 작위 |
| 기타 | 향후 서버 설정으로 추가 가능 |

정확한 공식과 Threshold는 아직 **밸런스 미확정**이다.

---

# 5. 개인 세력과 세력 가입

신규 플레이어는 자신의 닉네임을 기반으로 한 **개인 세력**으로 시작한다.

초기 상태는 `Tribe`다.

Tribe는 특수한 형태다.

**Tribe에는 다른 플레이어가 가입할 수 없다.**

성장 조건을 만족하면:

`Tribe → Minor Faction`

승격과 동시에 창립자가 **King**이 된다.

즉,

> Minor Faction 승격 + 최초 왕 즉위

는 하나의 원자적인 도메인 이벤트다.

이후부터 왕이 다른 플레이어를 세력에 받아들일 수 있다.

가입 플레이어는 최소 `Baron` 작위를 받아야 한다.

A가 B 세력에 가입하면:

`A의 개인 Faction 소멸 → A와 A의 정착지들이 B Faction으로 편입`

된다.

동맹과 세력 가입은 완전히 다른 개념이다.

---

# 6. 봉건 도메인

봉건 작위는 다음 순서를 가진다.

`Emperor > King > Duke > Marquess > Count > Viscount > Baron`

하지만 단순한 Rank 구조가 아니다.

핵심은 **Feudal Lineage**다.

예를 들어:

```text
Emperor
 ├─ King A
 │   ├─ Duke A1
 │   │   ├─ Marquess A1-1
 │   │   │   └─ Count A1-1-1
 │   │   └─ Marquess A1-2
 │   └─ Duke A2
 │
 └─ King B
     └─ Duke B1
```

이 트리 자체가 중요한 도메인 객체다.

### FeudalRelation

```text
SuperiorPlayer
        │
        ▼
Direct Vassal
```

세금은 이 **직속 관계**를 따라간다.

따라서

`King → Duke → Marquess → Count`

관계에서 King은 Duke에게 직접 과세한다.

King이 Count에게 직접 세금을 걷지는 않는다.

---

# 7. 작위 권한

작위 부여와 변경 권한은 **King 이상**만 가진다.

가능한 명령은:

`Appointment / Promotion / Demotion / Revocation`

이다.

Revocation은 단순히 직함을 없애는 동작이 아니다.

현재 요구에서는:

> **작위 박탈 = 세력 제명**

이다.

제명된 플레이어는 다시 자신의 이름을 기반으로 한 독립 Faction을 얻는다.

정착지는 유지한다.

현재 보유 자산을 기준으로 새 Faction Tier가 계산된다.

---

# 8. 정착지 제한

Player의 정착지 최대 개수는 작위와 연결된다.

예를 들어 최종 서버 설정은 개념적으로:

```text
Baron      = 2
Viscount   = ?
Count      = ?
Marquess   = ?
Duke       = ?
King       = ?
Emperor    = ?
```

형태가 된다.

실제 수치는 서버 설정에서 결정한다.

승진은 문제가 없지만 강등 또는 제명으로 SettlementLimit이 감소할 수 있다.

이 경우:

> 새 정착지 한도 이하가 될 때까지 초과 정착지를 King 또는 Emperor에게 양도해야 한다.

이 작업이 완료되어야 강등/제명 처리가 완료된다.

따라서 작위 변경은 사실상 하나의 **Transaction**이어야 한다.

---

# 9. Territory 도메인

두 종류의 영토가 존재한다.

### Faction Territory

외부 세력과의 관계에서 사용하는 국가 국경이다.

### Title Territory

같은 세력 내부에서 사용하는 봉건 작위령이다.

Faction Border의 반경은 **Faction Tier**에 따라 결정된다.

Title Territory의 반경은 **Title Rank**에 따라 결정된다.

둘 다 서버 설정 가능하다.

예를 들면:

```text
Faction Border
Tribe       → Radius 2
Minor       → Radius ?
City-State  → Radius ?
Nation      → Radius ?
Empire      → Radius ?
```

와 같은 형태다.

실제 숫자는 아직 결정하지 않는다.

---

# 10. 영토 생성 규칙

정착지가 국경의 원천이다.

즉:

`Settlement → Radius → Territory Tiles`

이다.

자동으로 빈 공간을 채우지는 않는다.

따라서:

```text
OOO     OOO

```

처럼 두 영토 사이에 비어 있는 타일이 존재하면 그대로 중립 지역으로 남는다.

연결하려면 중간에 새 정착지를 세워야 한다.

정착지가 파괴되면 해당 정착지가 제공하던 국경도 **즉시 소멸**한다.

---

# 11. 국경 충돌

Faction Tier 상승으로 Border Radius가 커질 때 기존 다른 세력의 영토와 충돌할 수 있다.

정해진 우선규칙은:

> **먼저 존재한 Territory가 우선한다.**

따라서 후발 국경은 기존 영토를 덮어쓰지 않는다.

이 규칙을 구현하려면 Territory Tile에 단순 Owner뿐 아니라 최소한 **영토 확정 시점 또는 Priority** 개념이 필요하다.

---

# 12. 월드맵 정보 모델

기존의 전통적인 Fog of War 구조는 폐기됐다.

월드맵에서는 다음 정보가 항상 공개된다.

| 정보 | 공개 |
|---|---|
| 정착지 위치 | 항상 |
| 정착지 생성/소멸 | 항상 |
| 세력명 | 항상 |
| 소유 Player | 항상 |
| Faction Tier | 항상 |
| Faction Border | 항상 |

숨겨지는 핵심 정보는 **Caravan**이다.

따라서 이 시스템은 앞으로

> **Strategic Vision & Caravan Detection**

이라고 명명하는 편이 적합하다.

---

# 13. Vision 도메인

정착지:

`Vision Radius = Border Radius`

캐러밴:

`Vision Radius = 구성원 중 Shooting이 가장 높은 Pawn`

을 기반으로 계산한다.

시야는 Player가 아니라 **Faction 단위**다.

그리고 Alliance끼리 실시간으로 공유한다.

따라서:

```text
Player Vision
      ↓
Faction Vision
      ↓
Alliance Shared Vision
```

구조가 된다.

---

# 14. Scout 상태

Caravan에는 전략 상태가 존재한다.

```text
Traveling
Scout
Ambush
Combat
Cooldown
```

Scout에는 제한시간이 없다.

사용자가 해제할 때까지 계속 정찰한다.

Scout 상태에서는 추가 시야 보너스를 얻는다.

사용자가 Scout를 취소하면 즉시 움직이는 것이 아니라 **Movement Lock 시간**을 거친다.

공격받으면 Scout는 즉시 해제되고 전투로 전환된다.

---

# 15. Ambush 상태

Ambush도 Scout와 유사한 지속 상태다.

목표는 전투 보너스가 아니라:

> **월드맵에서 캐러밴의 위치를 숨기는 것**

이다.

매복 탐지 확률은 최소 다음 요소를 가진다.

```text
Observer Shooting
Ambushed Caravan Entity Count
Server Configuration
```

관측자의 Shooting은 해당 캐러밴에서 가장 높은 Pawn 값을 사용한다.

Ambush Caravan의 규모는 **전체 개체 수**로 계산한다.

탐지 판정은 Faction별 독립적이다.

A가 발견했다고 해서 C도 반드시 발견하는 것은 아니다.

다만 A의 Alliance는 A의 탐지 결과를 공유한다.

한번 발견되면 해당 Ambush가 종료될 때까지 그 세력에게 계속 보인다.

---

# 16. 외교 도메인

Faction 간에는 최소 다음 관계가 존재한다.

| 관계 | 의미 |
|---|---|
| Neutral | 기본 상태 |
| Alliance | 동맹 |
| WarPending | 선전포고 후 대기 |
| War | 전쟁 |
| PostWarCooldown | 같은 세력 재선전포고 금지기간 |

여기서 Betrayer는 관계 상태라기보다 별도의 **Faction Status**다.

즉:

```text
DiplomacyRelationship
+
BetrayerStatus
```

를 별도로 관리해야 한다.

---

# 17. Alliance

Alliance는 Faction 전체에 적용된다.

A와 B가 동맹이면 양쪽 모든 구성원이 동맹으로 취급된다.

하지만 방문은 여전히 승인제가 유지된다.

Alliance는:

- 시야 공유
- 자유 국경 통행
- 전쟁 자동 참전

등을 제공한다.

자동 참전은 **1-Hop만 적용**한다.

즉:

```text
A ↔ B ↔ C
```

에서 A와 C가 직접 동맹이 아니라면 A의 전쟁에 C가 자동 참전하지 않는다.

---

# 18. Betrayer

Betrayer는 Faction 단위 Status다.

배신자 세력은:

- 이름 뒤에 `(배신자)` 표시
- 월드맵 정착지에 별도 표시
- 다른 세력이 선전포고 없이 공격 가능

상태가 된다.

피해를 입은 기존 동맹과의 Alliance는 즉시 파기된다.

다른 동맹은 유지된다.

BetrayerDuration이 지나면 자동 해제되거나 피해 Faction이 직접 해제할 수 있다.

추가 배신 행동을 하면 남은 기간이 증가한다.

---

# 19. Betrayal 판정

이 부분은 단순 Damage 기반으로 만들면 안 된다.

의도 기반 판정이 필요하다.

우선 요구는:

```text
Direct Intentional Attack → Betrayal
Accidental Friendly Fire → No Betrayal
Enemy-targeted AoE collateral damage → No Betrayal
```

이다.

따라서 이상적인 판정 정보는:

`Attack Command → Intended Target → Actual Damage`

의 관계를 추적해야 한다.

이 기능 구현이 지나치게 어렵다면 **AoE를 Betrayal 판정에서 제외**하는 것은 허용된 기술적 fallback이다.

---

# 20. War 도메인

정식 선전포고는 Faction의 **최고 작위 보유자**만 가능하다.

War Declaration 후 바로 전쟁이 시작되지 않는다.

```text
Neutral
   ↓ Declaration
WarPending
   ↓ Timer Expired
War
```

WarPending 시간은 **공격자 Faction Tier**에 따라 결정된다.

Pending 동안 양쪽 모두 공격할 수 없다.

공격 Faction의 캐러밴이 이미 방어자 영토 안에 있다면 즉시 퇴거된다.

---

# 21. 비정규 전쟁

하위 귀족이 왕의 정식 선전포고 없이 다른 Faction을 공격할 수도 있다.

그 행동은 막지 않는다.

대신:

```text
Unauthorized Attack
→ Faction vs Faction Hostility
→ Attacker Faction Betrayer
```

가 된다.

피해 Faction은 이후 협상을 통해 전쟁을 끝낼 수 있으며 Betrayer도 해제해줄 수 있다.

즉 WarEconomy는 플레이어의 행동을 시스템적으로 완전히 봉쇄하기보다 **행동의 정치적 결과를 발생시키는 구조**다.

이것은 전체 게임 설계에서 상당히 중요한 원칙이다.

---

# 22. Peace Treaty

전쟁 종료 방식은 두 종류다.

### 무조건 평화

양측 합의만으로 종료.

### 조건부 평화

한쪽이 특정 물품을 요구한다.

수락되면 RimWorld Quest와 유사한 시간 제한 의무가 생성된다.

```text
Peace Agreement
      ↓
Temporary Peace
      ↓
Tribute Quest
```

성공:

`Peace 유지`

실패:

`즉시 War 재개`

이 경우 재선전포고 Cooldown은 적용하지 않는다.

---

# 23. 동맹의 전쟁 협상

전쟁에 참전한 직접 동맹은 원래 전쟁 당사자를 대신하여 평화협정을 체결할 수 있다.

동맹이 체결한 평화는 **주 전쟁까지 종료**시킨다.

따라서 War 객체에는 단순 두 Faction만 저장하는 것보다:

```text
Primary Belligerents
Participating Allies
```

를 구분하는 것이 필요하다.

---

# 24. Faction 생존

정착지가 0이라고 해서 Faction이 즉시 사라지는 것은 아니다.

Caravan이 하나라도 생존해 있으면 Faction은 존속한다.

다만 보유 자산 규모에 따라 Tier는 재계산된다.

따라서:

```text
SettlementCount = 0
CaravanCount > 0

=> Faction Alive
```

이다.

정착지 전멸은 **전쟁 종료 조건**일 수 있지만 **세력 소멸 조건과 동일하지 않다.**

이 구분은 중요하다.

---

# 25. 통치자 제거와 봉건 분할

최고 통치자와 그 실질적 세력이 완전히 제거되는 경우 하위 봉건 트리는 소멸하지 않는다.

예를 들어:

```text
King
 ├─ Duke A
 └─ Duke B
```

에서 왕의 세력이 완전히 사라지면:

```text
Duke A Branch → Independent Faction A
Duke B Branch → Independent Faction B
```

처럼 분할된다.

각 Branch는 자체 정착지와 자산을 바탕으로 Tier를 다시 계산한다.

조건을 만족하면 최고 생존 공작이 King이 될 수도 있다.

---

# 26. Settlement 도메인

Settlement의 핵심 관계는:

```text
Settlement
 ├─ Owner Player
 ├─ Faction
 ├─ Local Time
 ├─ Inventory
 ├─ Pawns
 ├─ Buildings
 ├─ Animals
 ├─ Trade Configuration
 └─ Territory
```

이다.

하나의 Player가 여러 Settlement를 가질 수 있다.

---

# 27. 오프라인 Settlement

Owner가 Offline이면 정상적인 Local Simulation은 멈춘다.

하지만 서버 수준 상호작용은 계속 가능하다.

| 기능 | Offline Settlement |
|---|---:|
| 일반 방문 | 불가 |
| Visit Request | 불가 |
| 침공 | 가능 |
| Tax Caravan | 가능 |
| Auto Trade | 가능 |
| 월드맵 표시 | 가능 |
| 국경 | 유지 |

따라서 Settlement는 Offline이라고 완전히 비활성 객체가 되는 것은 아니다.

---

# 28. Tactical Session

방문과 전투는 별도의 세션 종류가 아니다.

하나의 `TacticalSession`이 관계 상태를 가진다.

예를 들어:

```text
Peaceful
   ↓ Intentional Attack
Hostile
```

이다.

이 구조가 방문 중 배신을 자연스럽게 처리한다.

---

# 29. Tactical Authority

현재 선호하는 기술 모델은:

```text
Map Owner Client
       │
       ├─ Full Simulation Authority
       │
Remote Player
       │
       └─ Command Input
```

이다.

Remote Player는 자기 Pawn에게 내릴 명령만 전송한다.

Map Owner가 실제 판정과 시뮬레이션을 수행한다.

그 결과를 Snapshot으로 Remote Client에 복제한다.

다만 이는 **요구사항이 아니라 Architecture Candidate**다.

특히 Offline Settlement 공격과 충돌하기 때문에 나중에 별도로 기술 검증해야 한다.

---

# 30. Tactical Pawn Control

각 Player는 자신의 Pawn만 직접 조작한다.

```text
Player A → Pawn A*
Player B → Pawn B*
Player C → Pawn C*
```

다세력 전투 역시 같은 원칙이다.

동맹군은 해당 타일에 직접 진입해야 참전한다.

---

# 31. Session Time Control

평화 상태에서는 참가자 모두가 속도 제어 가능하다.

정책은:

> **Last Input Wins**

이다.

A가 3배속을 누른 후 B가 Pause를 누르면 Pause가 된다.

적대 상태가 되면:

```text
Speed = 1x
Pause = Disabled
```

로 강제된다.

전투 종료 후 기존 속도로 자동 복원하지 않고 사용자가 다시 선택한다.

---

# 32. 정복

정착지에서 적대 Entity가 모두 사라지면 RimWorld 방식으로 승리 판정한다.

승자는 두 선택을 한다.

```text
Victory
 ├─ Occupy
 └─ Destroy
```

Occupy는 SettlementLimit을 초과할 수 없다.

소유를 선택하면 맵의:

- 건물
- 물품
- 동물
- 생존 Pawn

등의 소유권이 새로운 Owner에게 넘어간다.

Destroy를 선택하면 공격자가 Caravan을 구성해 떠난 뒤 Settlement가 파괴된다.

그 위치에는 일시적인 **Ruins Site**가 남고 서버 설정된 시간이 지나면 사라진다.

---

# 33. Tax 도메인

세금은:

`Direct Superior → Direct Vassal`

사이에서만 발생한다.

### TaxPolicy

| 속성 | 의미 |
|---|---|
| Superior | 징수 귀족 |
| Vassal | 직속 봉신 |
| TargetDef | 요구 물품 |
| Quantity | 요구 수량 |
| Cycle | 반복 주기 |
| LastCollection | 마지막 실제 징수일 |

주기는 예정일이 아니라 **실제 징수일 기준으로 재설정**된다.

---

# 34. Tax Collection

세금은 자동 이체되지 않는다.

실제 `Tax Caravan`이 정착지에 도착해야 한다.

일반 방문과 달리 Settlement Owner가 Offline이어도 가능하다.

거래와 비슷한 UI를 연다.

예:

```text
Tax:
Steel × 500
```

Settlement에 Steel이 300개라면:

`부족량 = Steel 200개의 현재 Vanilla Market Value`

를 계산한다.

징수자는 부족 가치 이하에서 다른 재산을 강제 징수할 수 있다.

---

# 35. Delinquency

Tax Caravan이 충분한 재산을 징수하지 못하면 Player에게 Delinquency가 발생한다.

Delinquency는 Settlement가 아니라 **Player 단위**다.

```text
TaxDelinquentValue += UnpaidValue
```

누적된다.

다음 징수에서:

`Current Tax + Accumulated Delinquency`

만큼 징수 가능하다.

따라서 체납이 충분히 커지면 고가의 Pawn이나 동물도 강제징수 대상이 될 수 있다.

---

# 36. Player Market

각 Settlement는 별도의 자동 상점을 구성할 수 있다.

```text
Settlement A
 ├─ Sell Orders
 └─ Buy Orders
```

재고와 Silver를 예약하지 않는다.

실제 거래 순간 존재하는 재고만 사용할 수 있다.

따라서 Sell 100을 등록했더라도 재고가 30이면 상대에게 30만 표시된다.

Buy Order도 실제 Settlement에 존재하는 Silver 범위 내에서만 체결된다.

---

# 37. Offline Trade

Offline Settlement도 자동 거래 가능하다.

거래 완료 즉시 서버상 실제 재고에 반영한다.

구매 물품은 방문자의 Caravan에 즉시 들어간다.

Settlement Owner가 재접속하면 각 거래별 Letter를 받는다.

Letter를 클릭하면 거래 결과 물품이 생성된 위치로 카메라를 이동시킨다.

---

# 38. NPC Market

NPC 시장 상태의 Key는 개념적으로:

```text
(NpcSettlementId, ItemDef)
```

이다.

따라서 같은 물건이어도 정착지마다 가격 상태가 다르다.

모든 Player는 동일 NPC Settlement의 동일 시장상태를 공유한다.

대량 구매:

`Sell Price ↑ Exponentially`

대량 판매:

`Buy Price ↓ Exponentially`

시간 경과:

`Price → Base Price`

로 천천히 회귀한다.

재고 재생성 자체는 Vanilla RimWorld 방식을 최대한 따른다.

---

# 39. ServerConfiguration 도메인

현재 거의 모든 Balance Rule을 설정화하는 방향이다.

예상되는 설정 영역은:

`WorldTime / TierThreshold / BorderRadius / TitleTerritoryRadius / SettlementLimit / TitleLimit / WarPending / WarCooldown / BetrayerDuration / ScoutBonus / AmbushFormula / TaxCycle / NPCMarketCoefficients / RuinsDuration ...`

등이다.

설정은 **서버 재시작 시 반영**하는 것을 기본으로 한다.

포맷(JSON 등)은 아직 설계 단계에서 결정하면 된다.

---

# 40. UI 도메인

사용자 기능은 하나의 **WarEconomy 통합 창**으로 모은다.

정확한 탭 구성은 아직 UX 설계 단계이지만 논리적으로는 최소:

```text
Overview
Faction / Feudal
Diplomacy
Economy
Tax
```

정도의 영역이 발생한다.

다만 최종 탭 개수 자체는 요구사항으로 고정하지 않는다.

목표는:

> **필요한 정보를 찾기 쉽고, 관련 조작을 같은 문맥에서 수행할 수 있는 UI**

이다.

Feudal 영역에서는 트리 UI가 필요하다.

Tier 승격 조건은 정확한 숫자로 표시한다.

---

# 41. 시스템의 핵심 도메인 관계

전체 구조를 압축하면 다음과 같다.

```text
Player
  │
  ├── owns ───────────── Settlement
  │                         │
  │                         └── creates Territory
  │
  ├── owns ───────────── Caravan
  │                         │
  │                         ├── Scout
  │                         └── Ambush
  │
  ├── belongs to ─────── Faction
  │                         │
  │                         ├── Tier
  │                         ├── Diplomacy
  │                         ├── War
  │                         └── BetrayerStatus
  │
  └── holds ───────────── FeudalTitle
                            │
                            └── FeudalTree
                                  │
                                  └── TaxRelation
```

그리고 동일 타일에 복수 Player가 들어가면:

```text
Settlement / World Tile
          ↓
   TacticalSession
          ↓
 Multiple Players
          ↓
Each controls own Pawns
```

가 된다.

---

# 42. 현재 도메인 분석에서 남은 미확정점

이제 **구조 자체의 Critical 충돌은 거의 없다.**

남은 것은 대부분 상세 정책이다.

- 정확한 Tier 승격/강등 공식과 Threshold
- 제국 승격에 필요한 구체적인 조건
- Title별 SettlementLimit
- Tier별 BorderRadius
- Title별 내부 영지 Radius
- Title별 임명 가능 개수
- WarPending 구체적 시간
- BetrayerDuration 및 증가 공식
- Scout/Ambush 정확한 공식과 Cooldown
- NPC 가격 상승/하락 수학식
- 서버 설정 파일 형식
- Offline 전투 Authority의 실제 구현 방식
- 부분 세금 징수 시 다음 Tax Cycle 기준일의 세부 정의
- 절도가 정확히 언제 Hostile/Betrayal로 판정되는지

마지막 두 항목 정도만 시나리오 분석 과정에서 다시 물으면 충분하다.

## 다음 단계

이제 요구공학 순서상 **시나리오 기반 분석**으로 넘어가겠다.

단순히 기능별 시나리오를 만드는 게 아니라, 실제 플레이에서 시스템 여러 개가 동시에 만나는 장면을 중심으로 분석하는 것이 좋다.

예를 들어 첫 시나리오는

**「신규 플레이어 성장 → 소국 승격 → 왕 즉위 → 다른 플레이어 가입 → 남작 임명」**

으로 시작해서,

**「정찰/매복」**, **「평화 방문 중 배신」**, **「정식 선전포고와 전쟁」**, **「오프라인 정착지 침공」**, **「세금 징수와 체납」**, **「정복과 영지 재편」**, **「오프라인 자동 거래」**

순으로 주요 경로와 예외 경로를 분석하면 된다.

이 과정에서 시나리오마다 **선행조건 → 정상 흐름 → 대안 흐름 → 실패/예외 → 결과 상태**를 추출하고, 그 결과를 그대로 다음 단계의 유스케이스 명세로 연결하겠다.

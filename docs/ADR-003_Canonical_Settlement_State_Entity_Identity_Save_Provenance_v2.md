Proposed ADR-003: Canonical Settlement State, Entity Identity, and Save Provenance (v2)Status: PROPOSED (Not Accepted)Decision Owner: Master (GPT-5.6 Sol)Project: WarEconomy / RimMulti1. Context & BaselineThis ADR defines the canonical representation of a RimWorld settlement, stable cross-process identity, and the validation of state provenance. It uses the Master-accepted B2-lite baseline: the canonical state relies on an immutable engine-produced material-state artifact, a durable server-maintained index, and an ordered typed cross-boundary operation journal. Arbitrary field-level RimWorld object merging is explicitly rejected.   2. Canonical Settlement Material-State RepresentationThe Canonical Settlement State is composed of three synchronized elements:Logical Settlement Materialization Artifact/Package: An immutable, hash-verified snapshot representing the target settlement. The concrete storage format (e.g., whether it is a target-only .rws or a custom extraction package) remains an implementation boundary and is validation-required.   Server Projection / Index: A durable server-side representation of essential settlement data (e.g., wealth, active pawns, trade inventory). It is not merely an in-memory cache; it must be completely durable and verifiable/rebuildable from the canonical artifact combined with committed operations.   Delta / Cross-Boundary Manifest: An ordered journal of typed operations (e.g., ingress/egress, ownership changes, trade) that must be applied during the next engine materialization.   3. Revision Hierarchy and the Pending Operation QueueTo prevent stale-save duplication and ensure transaction ordering, state is fenced using a strict revision hierarchy:CommittedSettlementStateRevision: The unified canonical head revision. It increments only when a checkpoint or cross-boundary delta is actually committed to the canonical state.   ArtifactRevision: The specific revision of the physical materialization artifact/package.   SettlementProjectionRevision: The revision of the durable server projection/index, updated synchronously with actual commits.   PendingOperationQueue: During an active Tactical material-state lease, any Auto Shop or Tax mutations targeting the settlement are placed in this queue. Queued operations are not canonical mutations and do not increment the CommittedSettlementStateRevision. Upon Worker publication, the server revalidates these queued operations against the new canonical index; valid operations are applied, and invalid ones fail/compensate. (Note: TBD-05 regarding partial tax collection semantics remains explicitly unresolved).   4. Cross-Process Entity IdentityBecause multiple RimWorld engines generate native IDs independently, stable cross-process identity is required.   Canonical EntityId Scope: A server-issued EntityId is required only for entities that are server-addressable, cross-boundary, externally referenced, or persistent (e.g., Factions, Pawns, Animals, traded/taxed Things). Internal, ephemeral engine map objects remain native to the artifact and are not explicitly journaled for every split/merge/destroy unless they cross a canonical boundary.   Native ID Binding Invariant: The architecture requires a stable 1:1 binding between the server-issued EntityId and the native engine loadID that survives materialization. Concrete implementations (e.g., a custom ThingComp or global mapping component) are proposed candidates and remain validation-required.   Canonical Faction Registry: Player Factions are globally identified by the server and explicitly projected into every materializing engine instance to prevent ID collisions during Faction joins, splits, or expulsions.   5. Hostile Input Validation BoundaryAn owner client's uploaded checkpoint/save is untrusted hostile input. A valid writer lease grants submission authority, not truth authority. Before an artifact becomes canonical, the server MUST enforce the following validation layers:   Content/version manifest verification.   Allowed serialized types/schema validation.   Size and complexity bounds checking.   Typed semantic reference validation.   Canonical EntityId namespace and collision checks.   Parent revision (CheckpointParentRevision), WriterLeaseId, and provenance verification.   Plausibility and audit policy enforcement (pending Master decision on G-Q2).

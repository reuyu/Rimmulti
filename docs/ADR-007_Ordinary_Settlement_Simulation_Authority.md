Proposed ADR-007: Ordinary Settlement Simulation Authority & TopologyStatus: PROPOSED (Not Accepted)Decision Owner: Master (GPT-5.6 Sol)Project: WarEconomy / RimMulti1. Context & BaselineThis ADR clarifies who is authorized to simulate ordinary time for a settlement and how that simulation is integrated into the canonical state. It addresses the gap identified in the architecture red-team review regarding owner-client execution.   2. Canonical Custodian vs. Leased Simulation WriterDedicated Server: Retains final Canonical Custody of the settlement graph. A client map is never the final Domain Authority (ADR-001).   Owner Client: Operates as a Leased Simulation Writer. The client may simulate ordinary local time (SRS §4.2) only while it holds a valid, server-issued WriterLeaseId.   3. Lease, Fencing, and SessionEpochWriterLeaseId / Fencing Token: Unifies the ADR-001 SessionEpoch and ADR-002 Worker generation logic. A settlement has at most one active WriterLeaseId at any time (ADR-006A).   Disconnect/Reconnect: If the owner client disconnects, the server revokes the WriterLeaseId. Ordinary simulation must undergo a hard stop (ΔL = 0) until a new lease is established.   4. Ordinary ↔ Tactical HandoffEviction (Client → Worker): When a lawful attack (FR-152) or approved visit (FR-098) occurs against an online owner, the server immediately revokes the owner's WriterLeaseId. The owner client is forced to upload its final fast-forward checkpoint. The Server then generates a MaterializationManifest and grants the lease to a Tactical Worker.   Rematerialization (Worker → Client): Upon Tactical conclusion, the Worker publishes the new artifact. The server revokes the Worker lease and grants a new WriterLeaseId to the owner client, instructing it to rematerialize from the newly published canonical artifact.   5. Master Decisions Required (Explicitly OPEN)The following decisions require Master policy input and are not resolved by this ADR:G-Q1: Multi-Settlement TopologyContext: A player can own multiple settlements (FR-034), but ADR-006A requires one LocalClock per execution island.   Option A (Player-scoped clock): All settlements owned by a player share one LocalClock. Consequence: Conquest requires reprojecting the acquired settlement onto the new owner's clock, modifying the ADR-006A rule that conquest does not reset L_s.Option B (One active settlement per client): Only one settlement simulates; others freeze. Consequence: Simple implementation, but degrades the vanilla multi-colony experience.Option C (Per-map virtualization): Validated engine design separating clocks internally. Consequence: High implementation and validation risk.   G-Q2: Ordinary Simulation Anti-Cheat & Residual Trust PostureContext: Wealth and Pawn counts simulate locally and drive Faction Tier (FR-015).   Option A (Plausibility Bounds & Audit): Accept owner checkpoints with heuristic delta validation (e.g., wealth cannot increase by 50,000 in 2 minutes), accepting residual cheat risk. Consequence: Lower server cost, relies on audits to catch subtle cheating.   Option B (Server-hosted Ordinary Simulation): Ordinary simulation runs inside Workers. Consequence: Maximum security, but directly contradicts SRS §4.2 and vastly increases server costs.G-Q6: Checkpoint Loss Window & Disconnect GraceContext: How much ordinary progress can be lost on a sudden client crash.   Option A (Strict interval): Checkpoints mandated every X seconds. Consequence: Bounds data loss but increases network load.Option B (Immediate hard stop): Simulation ends the millisecond the TCP socket drops. Consequence: Prevents uncommittable progress, but highly sensitive to micro-disconnects.Cross-ADR Contract DefinitionsTo prevent overlapping responsibilities, the architecture domains are explicitly partitioned as follows:ComponentOwning ADRDefinition & ResponsibilityLocalClockIdADR-006A / ADR-007Identity of the temporal domain (ADR-006A).

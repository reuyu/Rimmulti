# Settlement_Genesis_Authority_Decision_Brief_01.md

**Status:** DECISION BRIEF — DO NOT RESOLVE PRODUCT POLICY WITHOUT REQUIREMENT AUTHORITY
**Decision Owner:** Master (GPT-5.6 Sol)
**Project:** WarEconomy / RimMulti

## 1. Genesis Authority & Lifecycle Traces

The creation of the first canonical Settlement artifact occurs without a prior `CheckpointParentRevision`[cite: 5]. The architecture must govern who creates this initial state and how it binds to canonical identity.

**First Player / Personal Tribe Creation:**
Requires fresh materialization based on a Vanilla scenario. The server assigns the `PlayerId`, the initial `FactionId` (Tribe)[cite: 1], and authorizes the genesis operation.

**Founding an Additional Settlement:**
Originates from an existing Shared World Caravan[cite: 2]. This is an ADR-008 custody transfer from `TransitClockId` to a new `LocalClockId`, utilizing existing canonical `EntityIds` rather than creating assets from nothing[cite: 2, 6].

**Expulsion / Branch Split:**
These are Dedicated Server domain state transitions (ADR-001), not material artifact genesis[cite: 1, 3]. Expulsion creates a new personal `FactionId` and transfers ownership of existing Settlements[cite: 1]. Branch splits elevate surviving branches into new `FactionIds`[cite: 1]. The physical `.rws` MapSegments remain intact; only the projected `FactionDomainState` changes.

## 2. Trust Differences & Candidate Models

**Model A: Fully Server-Controlled Engine Host Genesis**
*   **Trust:** Absolute. The Dedicated Server (via an Engine Host) generates the initial `.rws` artifact. 
*   **Characteristics:** Zero client forgery risk. Requires Server to run RimWorld map generation.
*   **Validity:** Aligns perfectly with G-Q2 constraints on untrusted client input[cite: 11].

**Model B: Server-Approved Scenario Contract + Client Artifact + Strict Validation**
*   **Trust:** Low. The client generates the map locally and uploads it as a candidate.
*   **Characteristics:** Relies entirely on the Server's hostile-input validator to strip forged wealth, items, or pawn skills (G-Q2)[cite: 11]. Map layout is arbitrary, but economic boundaries are strictly clamped by the Server.

**Model C: Server-Generated Manifest/Seed + Client Materialization + Census Validation**
*   **Trust:** Medium. The Server issues a cryptographic seed and generation manifest.
*   **Characteristics:** The client builds the map, and the Server validates that the uploaded census (Pawn count, skills, total wealth) matches deterministic expectations. *Risk:* Vanilla RimWorld generation determinism is historically fragile.

**Model D: Existing-Custody Settlement Founding (Caravan)**
*   **Trust:** Absolute (Inherited).
*   **Characteristics:** Governed by ADR-004 and ADR-008[cite: 2, 6]. Assets already possess canonical `EntityIds`. The Server authorizes the transformation of World custody to Map custody.

**Model E: Hybrid by Genesis Type**
*   **Characteristics:** Model A or C for the initial starting scenario (where no prior custody exists), and Model D for all subsequent expansions.

## 3. Canonical Identity & Initial Binding

### Replacing `CheckpointParentRevision`
Because there is no prior material state, `CheckpointParentRevision` is replaced by an idempotent `GenesisAuthorizationToken` or `GenesisReceiptRevision` issued by the Server during the `PREPARED` phase of the genesis transaction (ADR-004)[cite: 5, 6].

### Assignment of Entities
1.  **`PlayerId`, `FactionId`, `SettlementId`, `LocalClockId`:** Generated by the Dedicated Server upon receiving the genesis intent[cite: 3, 7].
2.  **`ContentProfileFingerprint`:** Bound securely by the Server at authorization, guaranteeing the genesis artifact matches the allowed schema (ADR-006B)[cite: 8].
3.  **`StoreIncarnationId` / Stable `EntityIds`:** Once the initial artifact is accepted, the Server parses the starting pawns/items and mints canonical `EntityIds`, mapping them against the native ephemeral `loadID`s (ADR-003)[cite: 5].

### `PlayerGlobalStateSegment` Initialization
The `PlayerGlobalStateSegment` (containing Research, Ideology, etc.) is initialized by the Server concurrently with the first `MapSegment`. It receives a `PlayerGlobalRevision` entirely distinct from the `CommittedSettlementStateRevision`[cite: 5]. During materialization, the Engine Host composes the `MapSegment` with the `PlayerGlobalStateSegment`.

### Fraud Prevention (G-Q2)
To prevent forged starting wealth, the Server **must** strictly generate or recompute:
*   Starting Pawn count, skills, health, and traits.
*   Starting Inventory (weapons, apparel, items, silver).
*   *Note:* The exact terrain layout (mountains, trees) is generally economically safe to accept from a client if the total map wealth is audited.

## 4. Mandatory Invariants

*   No client chooses arbitrary canonical starting wealth/material.
*   First artifact has an explicit genesis authority/receipt, not an implicit trust exception.
*   `ContentProfileFingerprint` is strictly bound before generation/materialization (ADR-006B)[cite: 8].
*   All server-addressable entities (Pawns, valuable items) receive stable `EntityIds` upon canonical admission (ADR-003)[cite: 5].
*   Genesis `LocalClockId` identity is explicit; it does not prematurely decide final G-Q1 topology (ADR-006A)[cite: 7, 10].
*   `PlayerGlobalStateSegment` and `MapSegment` initial revisions are separated.
*   Faction/domain state remains exclusively Server authoritative (ADR-001)[cite: 3].
*   Retry/reconnect cannot create duplicate starting settlements/entities (ADR-004)[cite: 6].
*   The genesis operation is fully idempotent and auditable.

## 5. Evidence Plan (A/Sol Runtime Probes)

Dev A and Sol must deliver PoCs distinguishing deterministic generation from census validation:

1.  **Same Genesis Request Retry:** Submit identical genesis requests; ensure ADR-004 returns the terminal receipt without generating a duplicate settlement[cite: 6].
2.  **Crash During Generation:** Terminate client/Server mid-genesis; verify lock rollback and cleanup.
3.  **Client-Tampered Starting Artifact:** Client edits starting `.rws` to grant Level 20 Shooting. Server must deterministically quarantine or reject it (G-Q2)[cite: 11].
4.  **Profile Mismatch:** Client attempts genesis with unapproved mods; Server handshake fails (ADR-006B)[cite: 8].
5.  **Duplicate `EntityId` / Custody:** Attempt to spawn two starting settlements using cloned canonical pawn IDs; ensure hard rejection[cite: 5].
6.  **Re-run Same Seed/Scenario:** Assess if Vanilla RimWorld 1.6 can generate the exact same Pawn stats/gear twice from the same seed (proving if Model C determinism is viable, or if census bounds are mandatory).
7.  **First PlayerGlobal + Map Composition:** Verify the engine can load a starting `.rws` alongside an injected, isolated `PlayerGlobalStateSegment`.
8.  **Additional Settlement Founding:** Execute ADR-008 custody transfer from Caravan to new Map, assigning `LocalClockId` without invoking the scenario generator[cite: 2].
9.  **Server Restart:** Restart Server between genesis reservation and canonical admission; verify Reconciler recovery[cite: 6].

## 6. End State

*   **Architecture Options:** Model A (Server Host), Model B (Client + Val), Model C (Seed + Census), Model D (Caravan Transfer), Model E (Hybrid).
*   **Mandatory Invariants:** Explicit Server authority, decoupled revisions, strict profile binding, anti-forgery census limits, stable EntityIds.
*   **Unresolved Product Choices:** Exact starting limits for custom scenarios, G-Q2 hostile-client trust threshold, and inheritance policy for `PlayerGlobalStateSegment` upon Faction join.
*   **Recommended Runtime Evidence Order:** 
    1. Re-run Same Seed/Scenario (proves/disproves Model C determinism).
    2. Client-Tampered Starting Artifact (proves Model B boundary).
    3. First PlayerGlobal + Map Composition (proves baseline execution).
*   **Exact Freeze Point:** Master must select the specific Genesis Trust Model (A, B, C, or E) **before Genesis Production implementation begins**, as this dictates whether the Dedicated Server requires an embedded RimWorld Engine Host merely to onboard new players.

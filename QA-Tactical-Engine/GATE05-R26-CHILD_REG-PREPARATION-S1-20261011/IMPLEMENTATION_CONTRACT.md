# R26 독립 child 등록 계약 준비

현재 판정은 READ_ONLY_PREPARATION_COMPLETE이며 실행 PASS가 아니다. 동결 R25 WorkerBridge AB5AD60F…/selected Debug A9C31DB0…만 분석했다. A의 현재 R26 제안은 읽거나 협의하지 않았다. 모든 API/type 이름과 추가 carrier는 아래의 제안이며 승인·구현·현재 external schema가 아니다. 기존 config14/snapshot15/receipt11/descriptor7/task27와 native launcher를 변경하지 않는다.

별도 READ_ONLY receipt를 만들어 private하게 보관할 **현재 producer가 없다**. 실제 존재하는 발급 callsite는 WorkerBridgeBootstrapper:99–117의 한 시작 설정 descriptor→IssueAdmissionReceipt→TryInstallOperatorStartupConfig다. 그 receipt는 process 전체 active receipt에 한 번 설치되고 seal된다. 별도 child config를 찾거나 operator가 승인한 parent-child 조합을 공급하는 callsite는 이 소스에 없다. Factory IssueAdmissionReceiptFromBytes:4170–4298은 raw SHA·descriptor·config 관계를 검사하고 private declaration을 복사하며 IsTrusted=true를 설정한다. ValidateAdmissionReceipt:4301–4426은 그 봉인된 필드의 정합성을 검사한다. 이 사실은 실제 caller가 operator였다는 인증이나 보호 채널의 실행 증거가 아니다. Public wrapper로 receipt를 넘기거나 IsTrusted 플래그만 확인하는 것으로 이 공백을 메울 수 없다.

현재 stage producer:2059–2142는 simulator의 seal/current generation/authority/grant에서 task를 만들고 nonce와 channel secret을 RNG로 만든다. Task 파일과 protected result 파일은 부모 Tasks의 절대경로다. HandleLaunchOperatorValidator:2189–2347은 current task nonce와 선택적 task ID를 검사한 후 부모 active snapshot에서 exe/SHA/free-form ValidatorArguments/cwd를 선택한다. --task-file와 --nonce를 붙이며 cwd가 존재할 때만 WorkingDirectory를 설정한다. Bootstrap의7개 operator 옵션 consumer와 이 두 옵션의 frontend consumer는 연결되지 않았다. Public BindOperatorLaunchedProcess는 process identity를 등록하는 기존 경로이고 별도 child receipt의 issuer가 아니다. Filesystem channel의 실제 접근 권한·전달·누설 방지와 effective native root는 여기서 미관측이다.

## 발급→검증→캡처→조회→소비→폐기 제안

| 단계 | 실제 사실 | 필요한 좁은 제안/선행조건 |
|---|---|---|
| Produce | Bootstrap는 부모 declaration 하나만 발급한다 | Operator가 독립 READ_ONLY raw config14와 original7 declaration을 **별도로** 공급하고 parent-child pair를 승인하는 경로를 먼저 지정한다 |
| Validate | 기존 factory와 receipt validator가 raw SHA/config/approved7을 비교한다 | 그 기존 함수를 각각 호출하되 issuer/channel provenance를 별도 기록한다; SIMULATION의 role 교체로 child를 만들지 않는다 |
| Capture | receipt 내부 snapshot과 approved7은 immutable/copy형이다; task27은 mutable public DTO다 | private profile에 child receipt와 원문 approved7을 보관하고, current owned task27/path를 새 immutable projection으로 복사한다 |
| Lookup | 현재 launcher는 global parent snapshot만 읽는다 | 같은 component의 live private slot에서 task object identity+TaskId+generation+resultEpoch+SealedResultId로 조회한다; possession of DTO/plan은 등록 authority가 아니다 |
| Consume | 현재 launcher/process binding와 CompleteStageValidation의 isConsumed=true가 있다 | live slot을 READY→LAUNCHING→BOUND→CONSUMED로 전이시키며 같은 task의 중복 launch를 막는다; 실제 process 증거는 후속 native WP다 |
| Revoke | reset/grant/seal/tick/load/revoke/dispose의 invalidation이 분산돼 있다 | 모든 task replacement/epoch 변화/consumption/dispose에서 private task slot을 무효화한다; M07 구현 승인 없이 hook을 고치지 않는다 |

권장 local 형태는 per-component private `OwnedChildRegistration`과 private `OwnedTaskLaunchRegistration`이다. Public mutable DTO나 Dictionary를 registry의 backing storage로 두지 않는다. Separate child profile에는 승인된 child receipt와 원문 approved7 및 operator가 선택한 parent-child pairing의 provenance만 들어간다. Task slot에는 private profile reference, captured parent receipt, exact copied task27/path와 LIVE state가 들어간다. 별도 config/plan/origin 식별자를 registry가 생성하지 않는다. 기존 simulator의 TaskId/nonce/channel은 그대로 사용하며 새로운 cryptographic certificate 요구를 만들지 않는다.

Lookup 키는 `(owner component identity, currentGeneration, validatorTaskId, resultEpoch, sealedResultId)`와 동일 outstanding task reference다. TaskId·nonce·generation·epoch 등 모든 authority 필드의 실제 equality는 M05에서 승인·검증해야 한다. M04 PURE 복사 결과가 그 equality를 실행한 것처럼 보고하지 않는다. Reset가 epoch를0으로 돌리는 현재 사실 때문에 epoch 하나를 영구 unique key로 삼지 않는다. Operator child profile의 권장 수명은 한 owner startup provisioning이며 reset에서는 explicit reprovision을 요구하는 제안이다. Task slot은 각 stage/seal에 한 번 생성되고 completion/invalidations에서 끝난다. Reset/reprovision 정책은 Master가 채택할 때 확정한다. 오래된 immutable plan은 진단용 값으로 남을 수 있지만 live lookup 권한은 소멸한다. Scope-owned process 종료 및 채널 파일 정리는 native/M07의 별도 명시 계약이며 이번에 실행·보장하지 않는다.

## 실제 producer callsite 선택과 공백

선택 A는 기존 Bootstrap parent admission 성공 뒤, GameObject attachment 이전에 **operator-owned typed provider**가 별도 child raw config bytes/config path/SHA/original7을 공급하는 것이다. 그 provider는 소스에 존재하지 않는다. 현 schema14에는 child config path/origin/plan/configId를 담는 필드가 없고, 기존7 CLI는 그 process의 자기 선언만이다. 추가 CLI나 JSON bundle을 이미 지원하는 것처럼 만들지 않는다. Provider의 실제 producer, 전달 통로, 접근 권한, parent-child 승인 기록, Unity Awake 전에 seed를 안전하게 전달하는 순서를 Master가 지정해야 이 선택을 연결할 수 있다. AddComponent가 Awake를 언제 실행하는지 확인 없이 post-Awake 초기화를 약속하지 않는다.

선택 B는 부모가 정상 bootstrap된 후 owned controller의 **typed task-scoped callback**에서 별도 child receipt를 공급하는 것이다. 기존 HandleLaunchOperatorValidator의 nonce 검증 위치가 소비 권한을 확인하는 실제 근접 callsite이지만 현재 request는 free-form string이고 child declaration 등록 API/전달 carrier가 없다. 기존 nonce 값이나 filename만으로 새 payload의 발급 경로를 증명하지 않는다. Protected local pipe+unguessable current capability 또는 동등한 operator-owned channel은 MD126에서 허용되는 PoC 선택이며 이 저장소에 그 child provisioning 연결이 있다고 주장하지 않는다. Registration command를 public Bridge switch에 추가하거나 public BindOperatorLaunchedProcess를 issuer로 재활용하는 제안은 하지 않는다.

두 선택 중 A를 startup 선언의 기본 후보로 권고하되, 이번 첫 구현에는 issuer integration을 포함하지 않는다. 실제 producer/channel이 정해지면 다음 **private** signatures를 논의할 수 있다: `TryCaptureOwnedChildFromIssuer(OwnedChildProvisioning issuedPair)`, `CaptureForCurrentTask(OwnedChildRegistration profile, ValidatorTask currentOwnedTask, string currentTaskPath)`, `TryTakeCurrentOwnedLaunchPlan()`, `InvalidateOwnedChildTaskSlot(reason)`. ## 첫 최소 구현과 PURE seam

우선 `OperatorChildLaunchInputs.Capture(parentReceipt, separatelyAdmittedReadOnlyReceipt, task, taskPath)`라는 public PURE data-only seam을 제안한다. 기존 receipt의 internal Approved* 필드에서7을 읽으므로 caller의 추가 descriptor를 authority 입력으로 받지 않는다. 부모 SIMULATION과 child READ_ONLY의 기존 receipt 정합성을 검사한 후 snapshot15+receipt11+approved7+task27+taskPath를 local immutable 값으로 복사한다.
